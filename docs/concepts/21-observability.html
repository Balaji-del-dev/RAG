2Why it matters

When a user reports "the answer was wrong" or "it took 12 seconds", you need to see exactly what happened in that request: what was searched, what came back, what the prompt contained, what the model returned and which check failed. Without traces, debugging RAG is guesswork.

3Core ideas

Logs

Individual events ("job 812 failed: timeout"). Structured JSON with request and trace IDs.

Metrics

Numbers over time: p95 latency, error rate, abstention rate, queue length. Used for dashboards and alerts.

Traces

One request end to end, as a tree of timed spans with attributes. Used to debug a single answer.

4How it works

Metrics to track

Online

  • latency p50/p95/p99 per span; TTFT
  • errors and timeouts per dependency
  • abstention rate; empty-retrieval rate
  • tokens per answer; GPU utilization
  • feedback (thumbs up/down) rate

Ingestion

  • queue length and age (Celery / Flower)
  • failed jobs by step; retries
  • time from upload to searchable
  • index sync lag; reconciliation drift

Debugging a bad answer

  1. Find the trace by request_id (shown in the UI or support ticket).
  2. Check retrieval: was the right chunk in dense or BM25 results? At what rank? Did it survive fusion and reranking?
  3. Check the prompt: was the chunk included, and where? Was the context too long?
  4. Check the output and validation: which claim was unsupported? Did validation catch it?
  5. Add the case to the evaluation dataset once fixed (lesson 20).

5In the real world

  • Correlation IDs everywhere: request_id and trace_id in logs, traces and database rows.
  • Privacy by default: record IDs, scores, timings and token counts. Log raw prompts and document text only when policy allows, with redaction and short retention (lesson 24).
  • SLOs and alerts: for example "p95 under 4 s", "error rate under 1%", "ingestion backlog under 15 minutes". Alert on symptoms users feel.
  • Standards: OpenTelemetry has semantic conventions for generative-AI spans. LLM-focused tools (Langfuse and others) add prompt management, scores and evaluation views.

6Common mistakes

  • Only an overall latency number, with no per-stage breakdown.
  • Logging full prompts with personal data into a system with broad access.
  • No request ID in the UI, so user reports can't be matched to traces.
  • Monitoring the API but not the ingestion queue, so documents silently never become searchable.

8Check yourself

What is the difference between a metric and a trace?
A metric aggregates many requests over time (e.g. p95 latency). A trace shows one request in detail, as timed spans.
Users say answers are slow. Which span do you check first?
Usually llm.generate (TTFT and output tokens), then rerank. The per-span breakdown tells you where the time goes.
Why avoid logging raw prompts by default?
Prompts contain retrieved document text and user questions, which may include personal or confidential data. Logs are often widely accessible and long-lived.
