1What is observability?

Interview answer — say this first
In simple words

Observability means you can see inside every request: what was searched, what came back, what the prompt contained, what the model answered, how long each step took and which check failed. It uses three tools: logs (events), metrics (numbers over time) and traces (one request, step by step).

2Why do we need it?

When a user says "the answer was wrong" or "it took 12 seconds", you need to know exactly what happened in that one request. A RAG answer passes through many steps; any of them can fail. Without traces, debugging is guesswork.

Without observability

  • "It's slow" — but which step?
  • "The answer is wrong" — retrieval or the LLM?
  • Documents silently never become searchable

With observability

  • Time per step: search 30 ms, LLM 2.5 s
  • See which chunks were retrieved and used
  • Alerts when queues back up or errors rise
Analogy: a parcel tracking page

When a parcel is late, the tracking page shows every stop: picked up, sorted, left the hub, out for delivery — with times. A trace is the tracking page of one question: every step it went through, with times and details.

3How does it work?

1

Give every request an ID

Create a request ID and trace ID at the start and pass them to every service, log line and database row. Show the request ID in the UI so a user report can be matched to its trace.

2

Record each step as a span

A span is one timed step (search, rerank, LLM call) with useful details: model, top-k, number of hits, tokens, scores. The spans of one request form a trace.

3

Write structured logs

Log events as JSON with the request ID, such as "job 812 failed: timeout". Avoid logging raw personal data.

4

Collect metrics and set alerts

Track numbers over time: p95 latency, error rate, abstention rate, queue length. Set targets (SLOs) and alert when users would feel a problem.

5

Use traces to debug and improve

Find the trace of a bad answer, see which step failed, fix it, and add the case to the evaluation set (lesson 20).

Logssingle events · "job failed: timeout"
Metricsnumbers over time · p95 latency, error rate
Tracesone request · timed spans per step

The three pillars of observability. For debugging one RAG answer, traces matter most.

How to debug a bad answer

  1. Find the trace using the request_id from the UI or support ticket.
  2. Check retrieval: was the right chunk in the vector or BM25 results? At what rank? Did it survive fusion and reranking?
  3. Check the prompt: was the chunk included, and where? Was the context too long?
  4. Check the output: which claim was unsupported? Did validation catch it?
  5. After fixing, add the case to the evaluation dataset.

5Important terms

Log

A record of a single event, ideally structured JSON with a request ID.

Metric

A number measured over time, such as p95 latency or error rate.

Trace

The full path of one request, shown as a tree of timed spans.

Span

One timed step inside a trace, with attributes like model name and token count.

Correlation ID

An ID (request_id, trace_id) shared by all logs, spans and rows of one request.

p95 / p99 latency

95% (or 99%) of requests are faster than this. Shows the slow tail, unlike the average.

SLO

Service Level Objective: a target, such as "p95 under 4 seconds".

TTFT

Time to first token: how long until the answer starts appearing.

7Advantages and limitations

Advantages

  • Fast debugging of a single bad answer
  • Shows which step makes it slow
  • Alerts before users complain
  • Real failures feed the evaluation set

Watch out for

  • Logging prompts can store personal data
  • Too much data is costly to store
  • Alerts on everything → alerts get ignored
  • Langfuse v3 needs ClickHouse and runs as containers
Remember — privacy by default

Record IDs, scores, timings and token counts. Log raw prompts and document text only when the policy allows it, with redaction and a short retention period (lesson 24).

9How to explain it in an interview

Your 1-minute answer

DefinitionObservability is the ability to understand what a system is doing from the data it produces — logs, metrics and traces.

HowEvery request gets a request ID and trace ID that are passed to all services. Each step — query processing, vector search, BM25, fusion, reranking, LLM generation and validation — is recorded as a timed span with details such as model, top-k, scores and token counts.

ExampleWhen a user reports a wrong answer, I open its trace, check whether the right chunk was retrieved and at what rank, whether it reached the prompt, and which validation failed.

In productionI track p95 latency per step, error rates, abstention rate, tokens and ingestion queue lag with SLOs and alerts, and I avoid logging raw personal data by default.

Don't say"We log everything, including full prompts, forever."
Say instead"We log IDs, timings, scores and tokens by default; raw text only when policy allows, redacted, with short retention."
Don't say"Our average latency is fine."
Say instead"We track p95 and p99 per step, because averages hide the slow requests users notice."
