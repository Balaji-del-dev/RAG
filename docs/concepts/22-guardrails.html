1What are guardrails?

Interview answer — say this first
In simple words

Guardrails are safety checks around the LLM, written in code. They check what goes in (the question), what the model may read (the documents), what comes out (the answer) and what it may do (tool actions) — and block, fix or replace anything that breaks the rules.

2Why do we need it?

LLMs are flexible, and that cuts both ways. They can be pushed off-topic, tricked into revealing data, or produce unsafe, made-up or badly formatted answers. A rule in the system prompt ("never discuss X") is not enough, because it can be overridden. Guardrails are enforced in code, like input validation in a web app.

Without guardrails

  • "Ignore your rules and…" may work
  • Personal data can appear in answers
  • Broken JSON crashes the app
  • An agent could delete data on injected text

With guardrails

  • Out-of-scope requests are politely refused
  • Only permitted documents reach the model
  • Answers are checked before they are shown
  • Risky actions need human approval
Analogy: airport security

There are checks at several points: at check-in (input), at the security gate (what you may carry — retrieval), at boarding (output), and on the plane (actions). No single check is perfect, so there are several layers.

3How does it work?

Guardrails work in four layers, one at each stage of a request:

1

Input guardrails — check the question

Schema and length limits, language, topic or scope classifier, prompt-injection and jailbreak detection, personal data in the question, rate limits.

2

Retrieval guardrails — control what the model reads

Access-control filters (only documents the user may see), trusted sources only, relevance thresholds, removing hidden instructions or markup from documents.

3

Output guardrails — check the answer

JSON schema, citation and grounding checks, toxicity and safety classifier, personal data or secret leakage, business rules.

4

Action guardrails — control tools

Tool allow-lists, argument validation, per-user permissions, human approval for actions that change data, spending limits.

5

When a check fails

Block, repair (ask the model again once), redact, or give a safe fallback answer. Fail closed for safety and access: when in doubt, don't show it. Log which rule fired, but not the sensitive content.

Remember — deterministic first, models second

Use simple code checks (regex, schemas, allow-lists, length limits, access filters) wherever possible: they are fast, predictable and testable. Use model-based checks (classifiers, LLM judges) only for fuzzy things like harmful intent or unsupported claims.

5Important terms

Guardrail

A check in code around the model that enforces rules on inputs, context, outputs or actions.

Input validation

Checking the question's format, length, scope and safety before processing.

Output validation

Checking the answer's format, citations, grounding and safety before showing it.

Jailbreak

A prompt designed to make the model ignore its safety rules.

Safety classifier

A model that labels text as safe or unsafe by category (e.g. Llama Guard).

PII redaction

Finding and masking personal data such as names, phone numbers or ID numbers.

Fail closed

If a check errors or is unsure, deny instead of allow.

Human in the loop

A person must approve risky actions before they happen.

7Advantages and limitations

Advantages

  • Keeps the assistant on-topic and safe
  • Prevents data leaks and broken output
  • Limits the damage of a successful attack
  • Rules are enforced in code, not just requested

Limitations

  • False positives annoy users; false negatives cause incidents
  • Model-based checks add latency
  • Prompt injection has no complete fix
  • Need their own test set and maintenance
Remember — measure your guardrails

Build a test set of should-block and should-allow inputs. Track false positives and false negatives, and re-test after every model or prompt change.

9How to explain it in an interview

Your 1-minute answer

DefinitionGuardrails are programmatic checks placed around a language model that enforce rules on what goes into the model, what it may read, what it returns and what actions it may take.

LayersInput guardrails validate the question's format, scope and safety and detect injection. Retrieval guardrails apply access-control filters. Output guardrails validate the schema, citations, grounding, safety and data leakage. Action guardrails restrict tools and require approval for side effects.

DesignI prefer deterministic checks where possible because they are fast and testable, and use model-based classifiers for fuzzy risks. Safety and access checks fail closed.

Key pointGuardrails reduce risk but cannot eliminate it, so I measure false positives and negatives and design the system so that a bypass causes limited damage.

Don't say"A strong system prompt is our guardrail."
Say instead"Instructions can be overridden. Guardrails are enforced in code, and the damage of a bypass is limited by design."
Don't say"We block anything that looks risky."
Say instead"We measure false positives too; over-blocking makes users abandon the system."
