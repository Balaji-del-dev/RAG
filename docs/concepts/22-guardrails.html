2Why it matters

LLMs are flexible, and that cuts both ways: they can be steered off-topic, tricked into revealing data, or produce unsafe, ungrounded or badly formatted output. Guardrails are the checks around the model that keep the system inside its intended behaviour. They work like input validation and output encoding in classic web security.

3Core ideas: four layers

LayerChecksExamples
Inputbefore retrievalschema and length; language; topic/scope classifier; prompt-injection and jailbreak detection; PII in the question; rate limits
Retrievalwhat may enter the contextaccess-control filters; trusted sources only; relevance thresholds; strip instructions and markup from documents
Outputbefore the user sees anythingJSON Schema; citation and grounding checks; toxicity and safety classifier; PII or secret leakage; competitor or policy rules
Actionbefore any side effecttool allow-lists; argument validation; per-user permissions; human approval; spending limits

Deterministic first, models second

Deterministic

Regex, schemas, allow-lists, length limits, ACL filters. Fast, predictable and testable — use them wherever possible.

Model-based

Classifiers or LLM judges for fuzzy things: harmful intent, topic drift, unsupported claims. More flexible, but slower and probabilistic.

4How it works

Typical tools

  • Llama Guard (and similar safety classifiers): label a prompt or response as safe or unsafe, by category. Runs locally.
  • NeMo Guardrails: define conversation rails (allowed topics, flows, fact-checking steps) around an LLM.
  • Guardrails AI: validators for output (structure, PII, profanity, custom checks) with re-ask or fix behaviour.
  • Presidio: detect and anonymize PII (names, phone numbers, IDs) in text.

What happens when a check fails

  1. Decide: block, repair (re-ask once), redact, or fall back to a safe answer.
  2. Respond helpfully: "I can only answer questions about our HR documents", not a stack trace.
  3. Fail closed for safety and access checks: when in doubt, don't show it.
  4. Log the reason (which rule, which score) — but not the sensitive content itself.

5In the real world

  • Guardrails make mistakes in both directions. Measure them: build a test set of should-block and should-allow inputs; track false positives (annoyed users) and false negatives (incidents).
  • Budget their latency: run cheap checks in parallel with retrieval, and use model-based checks only where needed.
  • Guardrails reduce risk but don't remove it. Prompt injection in particular has no complete solution (lesson 23). Design so that a bypass does limited damage: least privilege, no secrets in prompts, human approval.
  • For RAG, the most valuable output guardrail is usually the grounding and citation check (lesson 18).

6Common mistakes

  • Relying only on a system-prompt instruction ("never discuss X") as a guardrail.
  • Blocking so aggressively that normal questions fail, so users stop using the system.
  • Checking input but not output, or output but not tool calls.
  • No tests for guardrails, so silent regressions follow model or prompt updates.

8Check yourself

Why prefer deterministic checks where possible?
They are fast, predictable, cheap and easy to test. Model-based checks are probabilistic and add latency.
Is a strong system prompt enough to stop misuse?
No. Instructions can be overridden or leaked. Guardrails must be enforced in code around the model, and the impact of bypasses limited by design.
What does "fail closed" mean for an access-control check?
If the check errors or is uncertain, deny access instead of allowing it.
