2Why it matters

Models never see letters or words, only token IDs. Context limits, chunk sizes, latency and cost are all measured in tokens. If you size things in characters and the model counts tokens, text gets silently cut off and answers get worse without any error message.

3Core ideas

A token is a piece of text from a fixed vocabulary

A tokenizer has a vocabulary of roughly 32,000–200,000 pieces. Common words are one token; rare words are split into several pieces:

thethe1
unbelievableun believ able3
" Paris" (with space)␣Paris — the space is part of the token1

Exact splits depend on the tokenizer. Every model family has its own, so always count with the tokenizer of the model you use.

How BPE builds the vocabulary

  1. Start with single bytes or characters.
  2. Count which adjacent pair appears most often in the training text (for example t+h).
  3. Merge that pair into a new token (th), and repeat thousands of times (th+e → the, …).
  4. Stop when the vocabulary reaches its target size.

Variants include byte-level BPE (GPT-style, tiktoken), SentencePiece (Llama, Gemma) and WordPiece (BERT-style encoders). Byte-level tokenizers can encode any text; nothing is ever "unknown".

Rules of thumb

  • English: about 4 characters or 0.75 words per token. 1,000 words ≈ 1,300 tokens.
  • Many other languages — including Tamil, Hindi and other Indic scripts — need 2–4× more tokens for the same meaning with many tokenizers. That means more cost, slower answers and less room in the context.
  • Numbers, IDs, code and URLs tokenize into many small pieces. This is one reason models are weak at exact arithmetic and long identifiers.

4How it works in an application

Special tokens and chat templates

Instruct models expect a specific chat template made of special tokens that mark roles, for example <|im_start|>system … <|im_end|>. Serving tools (Ollama, vLLM) read the template from the model files and apply it for you. A wrong template makes a good model behave badly.

Input tokens vs output tokens

  • Prefill: all input tokens are processed in parallel. Fast per token.
  • Decode: output tokens are produced one at a time. Slow per token.

So long answers cost more time than long prompts. Output tokens usually dominate latency.

Count tokens properly

from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("path/to/local/model")   # same model you serve
n = len(tok.encode(chunk_text, add_special_tokens=False))
assert n <= 512, "chunk too long for the embedding model"

5In the real world

  • Embedding models have their own limits, often 512 or 8,192 tokens. Text past the limit is usually truncated silently — the end of a chunk simply isn't embedded.
  • Configure chunk sizes in tokens of the embedding model, not characters (lesson 11).
  • Record token usage per request: it explains latency and cost, and catches runaway prompts.
  • Long contexts are not free: more tokens means slower prefill, more GPU memory (KV cache, lesson 04), and often lower answer quality (lesson 18).

6Common mistakes

  • Estimating with len(text) / 4 for hard limits. Fine for rough planning, wrong for enforcement.
  • Not reserving room for the answer, so it gets cut off mid-sentence.
  • Measuring chunks in characters while the embedder truncates at 512 tokens.
  • Forgetting that multilingual text needs more tokens per sentence.

8Check yourself

Why might a Tamil document cost more to process than an English one of the same length?
Many tokenizers were trained mostly on English, so Indic scripts get split into more, smaller tokens. More tokens means more compute, more latency and less room in the context.
Why does answer length affect latency more than prompt length?
Input tokens are processed in parallel (prefill). Output tokens are generated one by one (decode).
A chunk has 900 tokens and the embedding model's limit is 512. What happens?
Usually the last ~388 tokens are silently dropped from the embedding. Questions about that part won't match the chunk.
