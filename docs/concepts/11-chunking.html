2Why it matters

The chunk is the unit that gets embedded, retrieved, ranked and cited. Chunks that are too big give blurry vectors, waste tokens and make citations vague. Chunks that are too small lose the context needed to understand them ("it must be filed within 10 days" — what must?). Chunking is one of the highest-impact, cheapest settings to tune.

3Core ideas

Why chunk at all

  • Model limits: embedding models accept 512–8,192 tokens (lesson 02).
  • Precision: one vector for a 40-page document averages everything and matches nothing well.
  • Context budget: you can fit 5–10 focused chunks in a prompt, not 5 whole documents.
  • Citations: chunk-level provenance points to a page and section.

Strategies

StrategyHowGood for
Fixed-sizeevery N tokens, with overlapquick baseline, uniform text
Recursivesplit on the largest separator that fits (headings → paragraphs → sentences → words)a strong general default
Structure-awarefollow document structure: sections, lists, tables, slides, rowsmanuals, policies, contracts — anything with headings
Semanticsplit where embedding similarity between neighbouring sentences dropslong unstructured prose; more compute
Parent-child (small-to-big)embed small child chunks for precise matching; give the LLM the larger parent sectionprecise retrieval and enough context
Sentence windowembed single sentences; return them with neighbouring sentencesfact lookup in dense text
Late chunkingembed the whole document with a long-context model, then pool token vectors per chunkkeeping document context in each chunk vector

Give every chunk its context

A chunk like "The fee is ₹500 per month" is useless without knowing which fee. Two cheap, effective fixes:

  • Contextual chunk header: prepend the title and section path before embedding — "Pricing guide › Enterprise plan › Support add-on: The fee is ₹500 per month."
  • Contextual retrieval: a model writes one sentence situating each chunk within its document, and it is prepended before both embedding and BM25 indexing. Anthropic reported this cut failed retrievals by about half, and by about two thirds combined with reranking. It costs one LLM call per chunk at ingestion time.

4How it works: choosing settings

ContentStarting point
FAQ, short factual answers150–300 tokens, small overlap, or one chunk per Q&A pair
Policies, manuals (headed sections)structure-aware, 300–800 tokens, parent-child for long sections
Contracts and legal textby clause or section; keep numbering in the header
Tableswhole table if small; row groups with repeated headers if large
Codeby function or class (syntax-aware splitters)
Chat logs and emailsby message or thread, with sender and date metadata

Typical overlap is 10–20%. Overlap protects sentences that cross a boundary, but too much overlap fills the top-k with near-duplicates.

Test, don't guessBuild 50–100 evaluation questions with known answer locations. Compare recall@k (lesson 20) for 2–3 chunk settings. The best size depends on your documents and questions.

5In the real world

  • Measure chunk size in tokens of the embedding model, and keep chunks under its limit.
  • Never split inside a table row, a code block or a numbered clause.
  • Store for every chunk: document version, chunk index, pages, section path, token count and content hash. Keep parent and neighbour links too.
  • Deterministic chunk IDs (hash of version, pipeline version, index and content) make re-runs idempotent.
  • Validate chunks: drop empty, boilerplate-only or duplicate chunks; flag oversized ones.

6Common mistakes

  • One fixed size for every document type.
  • Chunks without context, full of "this", "it" and "the above".
  • Huge overlap that returns three copies of the same text.
  • Changing chunking without re-running the evaluation set.

8Check yourself

What problem does parent-child chunking solve?
Small chunks match queries precisely but lack context; large chunks have context but match poorly. Parent-child retrieves with small chunks and gives the LLM the larger parent section.
Why prepend the title and section path to a chunk before embedding?
It adds the missing context ("which plan, which policy") to both the vector and the keywords, so the chunk matches questions that name the topic.
Why can large overlap hurt?
Neighbouring chunks become near-duplicates, crowd the top-k results and waste the context budget.
