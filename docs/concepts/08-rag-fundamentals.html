2Why it matters

Most real-world LLM applications need answers about private, changing, specific information: company policies, contracts, manuals, tickets, medical guidelines. The model never saw this data (lesson 01). RAG fetches the relevant passages at question time, puts them in the prompt, and asks the model to answer from them with citations.

3Core ideas

Question→ Retrievesearch your documents→ Augmentput passages in the prompt→ Generateanswer from them, with citations

Why RAG

  • Fresh and private knowledge without retraining: update the index, not the model.
  • Traceability: every claim can point to a document, page and version.
  • Access control: retrieve only what the user is allowed to see.
  • Smaller models suffice: the model needs reading skills, not memorized facts.

Rule of thumbRAG for knowledge; fine-tuning for behaviour. They combine well.

4How it works: the two halves

Offline: ingestion (lessons 09–14)

  1. parse files and OCR
  2. clean and add metadata
  3. chunk
  4. embed
  5. index (vector + BM25)
  6. validate and publish

Online: per question (lessons 15–18)

  1. understand and rewrite the query
  2. hybrid retrieve
  3. fuse and rerank
  4. assemble context
  5. generate with citations
  6. validate or abstain

The seven failure points

A well-known study of real RAG systems (Barnett et al., 2024) lists where they fail:

#FailureTypical causeLesson
1Missing content — the answer isn't in the corpusgap in the documents; the model should abstain18
2Missed top-ranked documentsbad chunking, embeddings or query11–16
3Not in context — retrieved but cut during assemblytoken budget, too many candidates18
4Not extracted — in context but the model missed itnoise, conflicting passages, lost in the middle17–18
5Wrong formatweak output instructions, no schema05, 07
6Incorrect specificity — too general or too detailedprompt, question understanding07, 15
7Incomplete answersmulti-part questions, missing chunks15, 19
Debug in this order
  1. Is the answer in the corpus? If not, the system should abstain.
  2. Is the right chunk in the top-k candidates? If not, fix parsing, chunking, embeddings or the query.
  3. Did it reach the prompt? If not, fix reranking or context assembly.
  4. Did the model use it correctly? If not, fix the prompt or the model.

5In the real world

  • Typical uses: internal knowledge bases, customer support, HR and policy assistants, contract and legal search, engineering runbooks, product manuals, research libraries.
  • Retrieval quality is usually the bottleneck, not the LLM. Most of the work goes into parsing, chunking and search.
  • Start simple: good parsing, sensible chunks, hybrid search, a reranker, a strict prompt and an evaluation set. Add advanced patterns only when evaluation shows a need (lesson 19).

6Common mistakes

  • Tuning the prompt when the real problem is that the right chunk was never retrieved.
  • No evaluation set, so every change is judged by "it looks better".
  • Letting the model answer from its own memory when the sources are silent.
  • Building agents and graphs before a solid baseline exists.

8Check yourself

A user asks something your documents do not cover. What should a good RAG system do?
Abstain clearly: say the documents don't contain the answer, and possibly ask a clarifying question. It should not answer from the model's memory.
The correct chunk is in the prompt, but the answer is still wrong. Which part do you investigate?
Generation: the prompt, context noise and ordering, or the model. Retrieval did its job (failure point 4, "not extracted").
When would you choose fine-tuning over RAG?
When you need to change behaviour, style, output format or domain-specific language — not to add facts that change or need citations.
