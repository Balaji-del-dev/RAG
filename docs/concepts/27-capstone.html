1What is RAG system design?

Interview answer — say this first
In simple words

In a system-design interview you are asked: "Design a RAG assistant for our company." You must explain, step by step, how documents get in (ingestion), how questions get answered (query), how you prove it works (evaluation), and how you keep it safe, fast and cheap. This lesson puts all 26 lessons together into that answer.

2Why do we need it?

Senior AI interviews almost always include a design question. The interviewer is checking whether you can connect the pieces, make trade-offs and think about production — not just name tools. A clear structure makes your answer calm and complete.

Weak answer

  • "Put the documents in a vector DB and call GPT."
  • No requirements, no numbers
  • No evaluation, security or failure handling

Strong answer

  • Asks about users, documents, scale and limits first
  • Draws two pipelines: ingestion and query
  • Explains trade-offs, evaluation, security, scaling

3How does it work?

The 7-step framework for any design question

1

Clarify the requirements

Who are the users? Which documents (types, languages, scans)? How many documents and questions per day? Latency target? Access rules? Must it run offline? Citations required?

2

Estimate the scale

Number of chunks, vector memory, peak questions per second, GPU needs. Simple maths shows you think about cost.

3

Draw the ingestion pipeline

Upload → validate → store → parse/OCR → clean + metadata → chunk → embed → index → validate + publish (lessons 09–14).

4

Draw the query pipeline

Validate → understand the query → hybrid search → fuse → rerank → assemble context → generate with citations → validate or abstain (lessons 15–18).

5

Explain the data model and storage

A relational database as the source of record, object storage for files, a vector index and a keyword index as derived, versioned copies.

6

Explain quality: evaluation and observability

Golden dataset, retrieval and generation metrics, release gate, end-to-end traces and alerts (lessons 20–21).

7

Cover safety, privacy and scale

Access control at retrieval, guardrails, prompt-injection defences, deletion, latency budget, caching, reliable jobs, blue-green indexes, fallbacks (lessons 22–25).

4Example: step by step

"Design an HR policy assistant for 5,000 employees, fully offline"
  1. Requirements: 2,000 policy PDFs (some scanned), English and Tamil, answers with page citations, employees see only documents for their country, p95 under 4 seconds, no data leaves the company.
  2. Scale: 2,000 docs × ~60 chunks ≈ 120,000 chunks; 1,024-dim float32 vectors ≈ 0.5 GB — small. Peak ≈ 5 questions per second. One or two GPUs for the LLM.
  3. Ingestion: upload to object storage, record a job and outbox row in PostgreSQL, Celery workers parse with PyMuPDF + Docling, OCR only scanned pages, structure-aware chunks of ~500 tokens with headers, a multilingual embedding model, index into Qdrant and OpenSearch with country as a filter field.
  4. Query: condense follow-ups, run vector and BM25 search in parallel with the employee's country filter, fuse with RRF, rerank the top 40 with a cross-encoder, send the best 5 to a local LLM via vLLM with a citation prompt at low temperature, validate citations and grounding, or abstain.
  5. Quality: a golden set of 200 questions (English + Tamil, plus unanswerable ones), recall@10 and faithfulness tracked per release, Langfuse traces with request IDs.
  6. Safety: access filters in both indexes, safe output rendering, no secrets in prompts, audited deletion across all stores.
  7. Production: latency budget, embedding and retrieval caches, blue-green index generations, BM25-only fallback if the vector DB is down.

5Important terms

Functional requirements

What the system must do: answer from documents, cite pages, support Tamil.

Non-functional requirements

How well: latency, availability, security, cost, offline operation.

Back-of-the-envelope estimate

Quick maths for chunks, memory, traffic and GPUs.

System of record

The authoritative data store (here PostgreSQL); indexes are derived from it.

Index generation

One versioned, complete build of the search indexes that can be published or rolled back.

Release gate

Evaluation thresholds and approval that a change must pass before going live.

End-to-end trace

The record of one request across every step and service.

Trade-off

A choice that improves one thing at the cost of another, e.g. reranking: quality vs latency.

7Advantages and limitations

What makes a design answer strong

  • Starts with questions and numbers
  • Two clear pipelines on the whiteboard
  • Explains every trade-off it makes
  • Covers evaluation, security and failures

Common mistakes

  • Jumping to tools before requirements
  • Ignoring access control and deletion
  • No way to measure quality
  • No plan for model or index changes

9How to explain it in an interview

Your 2-minute design answer

ClarifyFirst I would clarify the users, document types and languages, scale, latency target, access rules and whether data may leave the company.

IngestionFiles are uploaded to object storage, and a job is recorded with an outbox row in PostgreSQL. Workers parse and OCR where needed, clean and add metadata, split documents into structure-aware chunks, embed them, and index them in a vector store and a keyword index as a new versioned generation that is validated before publishing.

QueryThe question is validated and condensed, vector and BM25 search run in parallel with the user's access filters, results are fused with RRF and reranked by a cross-encoder, and the best chunks go into a grounded prompt. The answer is validated for citations and grounding, or the system abstains.

Quality and operationsA golden dataset and release gate measure retrieval and generation quality, traces cover every step, and the system uses a latency budget, caching, idempotent jobs, blue-green indexes, graceful fallbacks, access control at retrieval and complete deletion.

Don't say"We'll use LangChain and a vector database."
Say instead"Here are the two pipelines, the data model, how we evaluate, and the trade-offs. Tools come after the design."
Don't say"It will just work."
Say instead"We define success metrics up front and gate every release on a golden dataset."
