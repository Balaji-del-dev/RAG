1What you will learn

  • Text normalization: Unicode, whitespace, hyphenation and encoding repair.
  • Removing boilerplate and duplicates that pollute search results.
  • Which metadata to capture, and how retrieval uses it.
  • Provenance: tracing every chunk back to its source.

2Why it matters

Raw extracted text is noisy: repeated footers on every page, broken words, odd Unicode, duplicate copies of the same policy. Noise wastes tokens and confuses search. Metadata is what lets you filter ("only 2026 HR policies"), cite ("page 4 of v3") and enforce access.

Boilerplate and noise

  • Headers, footers and page numbers repeated on every page: detect lines that repeat across many pages and remove them.
  • HTML navigation, cookie banners and "related articles".
  • Long legal disclaimers repeated in every email or document: keep one copy, or tag them.

Deduplication

  • Exact duplicates: same SHA-256 of the file or the normalized text.
  • Near-duplicates: same content with small edits. Find them with MinHash or SimHash, or with high embedding similarity.
  • Versions: a new upload of a known document becomes a new version; the old one is superseded, not duplicated.

Metadata comes from three places: extracted (file properties, headings), enriched (a local model classifies type, topic or language) and provided (the uploader picks a department).

Provenance

Every chunk should answer: which document, which version, which page and section, which parser, which pipeline version produced me? This makes citations trustworthy, deletions complete and bugs traceable.

5In the real world

  • Index only the metadata you will filter or display. Every extra field costs storage and index size.
  • Prefer a few controlled values (enums) over free text for filterable fields.
  • Enrichment with a local LLM is useful but costs time. Run it as an optional pipeline step and cache it by content hash.
  • Detect PII during ingestion if your policy requires it (lesson 24).

6Common mistakes

  • Lowercasing or stripping stored text, then showing ugly citations.
  • Keeping repeated footers, which then appear as "relevant" chunks for many questions.
  • Treating a new version as a new document, so both versions answer and contradict each other.
  • Free-text metadata that can't be filtered reliably.

8Check yourself

Why can repeated footers hurt retrieval?
They appear in many chunks, match many queries weakly, and take up top-k slots and tokens without adding information.
What is the difference between a duplicate and a new version?
A duplicate is identical content (same hash) and needs no reprocessing. A new version is changed content of the same logical document: it replaces the old version, which becomes superseded.
