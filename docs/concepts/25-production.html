2Why it matters

A demo answers one question nicely; production answers thousands a day, during deployments, model upgrades and partial outages. The difference is engineering: predictable latency, no lost work, safe changes and controlled cost.

Caching

Embedding cache

Key = content hash + model version. Unchanged chunks are never re-embedded.

Query / retrieval cache

Key = normalized query + filters + index generation. Short TTL; invalidate on publish.

Answer / semantic cache

Reuse answers for near-identical questions. Must include the user's access scope and generation in the key — otherwise it leaks or goes stale.

Prefix (KV) cache

vLLM and others reuse computation for a shared prompt prefix. Keep stable instructions at the start of the prompt.

4How it works: reliable background work

  1. Durable intent: write the job and an outbox row in one database transaction. Dispatch afterwards — see architecture diagram 02.
  2. Idempotent tasks: deterministic IDs and upserts, so running a task twice is harmless.
  3. Retries with backoff for transient errors; dead-letter after N attempts, with the error kept.
  4. Reconciliation: periodically compare PostgreSQL with Qdrant and OpenSearch (counts, missing or orphaned IDs) and repair the drift.
  5. Backpressure: queue limits and priorities, so a bulk upload doesn't starve interactive work.

Index versioning (blue-green)

Build a new index generation next to the live one, validate it, switch with one database commit, and keep the old one for rollback. Users never see a half-built index (architecture diagram 02).

Scaling and degradation

  • Stateless API workers scale horizontally; GPU capacity is planned from concurrency × context length (lessons 04, 06).
  • Connection pooling for PostgreSQL (e.g. PgBouncer); replicas for the search engines when needed.
  • Timeouts on every call and circuit breakers. Degrade gracefully: BM25-only if the vector DB is down, skip the reranker if it times out, abstain if the LLM is unavailable.

5In the real world

  • Cost is mostly GPU time. Levers: smaller models where evaluation allows, quantization, batching, caching, shorter prompts, and routing simple questions to cheaper paths.
  • Backups: point-in-time recovery for PostgreSQL and versioned object storage. Search indexes can be rebuilt, but measure how long a rebuild takes.
  • Safe changes: immutable configuration versions, evaluation gates, staged rollout and quick rollback.
  • Capacity tests: load-test with realistic prompt lengths and concurrency before launch.

6Common mistakes

  • No timeouts, so one slow dependency hangs every request.
  • Answer caches that ignore user permissions or index generation.
  • Dispatching tasks before the database commit, losing work on a crash.
  • Rebuilding the live index in place.
  • Never testing restore from backup.

7In our platform

Where this lives

  • outbox_events + dispatcher → Redis → Celery (idempotent tasks, retries, Flower monitoring); processing_jobs and index_build_jobs track attempts.
  • index_generations + index_validations for blue-green publication and rollback; reconciliation repairs index_memberships drift.
  • Immutable pipeline_versions; release gated by the evaluation loop; audit_events for changes.

8Check yourself

Why must an answer-cache key include the user's access scope?
Otherwise an answer built from documents one user may see can be served to another user who may not.
What does reconciliation protect against?
Drift between the system of record and derived indexes after partial failures — missing, duplicate or orphaned records.
The vector database is down. What is a graceful fallback?
Answer from BM25 results only (marked as degraded) or abstain, instead of failing every request.
