1What does "production-ready RAG" mean?

Interview answer — say this first
In simple words

A demo answers one question nicely. A production system answers thousands of questions a day — during deployments, model upgrades and partial outages — fast, reliably and at a controlled cost. Production engineering is the set of techniques that make this possible: latency budgets, caching, reliable background jobs, safe index updates, scaling and fallbacks.

2Why do we need it?

Demo-quality system

  • Sometimes takes 15 seconds
  • A crash loses uploaded documents
  • Re-indexing breaks search for an hour
  • One slow service hangs everything
  • GPU bill grows without control

Production system

  • p95 under a target, e.g. 4 seconds
  • No lost work: durable, retried jobs
  • New index built alongside, switched in one step
  • Timeouts and graceful fallbacks
  • Caching, right-sized models, cost tracking

3How does it work?

1

Set a latency budget

Decide the total target (e.g. p95 ≤ 4 s) and give each step its share. Run independent steps in parallel, such as vector and BM25 search.

2

Cache at every level

Embedding cache, retrieval cache, answer (semantic) cache and the LLM's prefix cache — each with the right key and expiry.

3

Make background work reliable

Write the job and an outbox row in one database transaction; make tasks idempotent (safe to run twice); retry with backoff; and regularly reconcile the database with the indexes.

4

Update indexes safely (blue-green)

Build a new index generation next to the live one, validate it, switch with one database commit, and keep the old one for rollback.

5

Scale and degrade gracefully

Scale stateless API workers horizontally; plan GPUs from concurrency × context length. Put timeouts on every call, and fall back (e.g. BM25-only) when a service is down.

6

Control cost

Cost is mostly GPU time: use smaller or quantized models where evaluation allows, batching, caching, shorter prompts, and route simple questions to cheaper paths.

5Important terms

Latency budget

The total time target split across the steps of a request.

Semantic cache

Reuses an answer for a question with very similar meaning.

Transactional outbox

Save the work and a "message to send" in one transaction, and send it afterwards, so no work is lost.

Idempotent task

A task that gives the same result if it runs twice, so retries are safe.

Reconciliation

A regular job that compares the database with the indexes and fixes differences.

Blue-green deployment

Build the new version next to the old one, then switch in one step, with easy rollback.

Circuit breaker

Stops calling a failing service for a while, so it doesn't slow everything down.

Backpressure

Limits and priorities on queues so a bulk upload doesn't block interactive work.

7Advantages and limitations

Advantages

  • Predictable speed for users
  • No lost work after crashes
  • Safe, reversible index and model changes
  • Controlled cost

Trade-offs

  • More moving parts to build and operate
  • Caches can serve stale or wrong-scope answers if keys are wrong
  • Blue-green needs double index storage for a while
  • Fallbacks give lower-quality answers
Remember — common production mistakes

No timeouts; answer caches that ignore user permissions; sending tasks before the database commit; rebuilding the live index in place; never testing a restore from backup.

9How to explain it in an interview

Your 1-minute answer

DefinitionProduction readiness means the system meets its latency, reliability and cost targets under real load, during failures and during changes.

LatencyI set a budget such as p95 under four seconds, run vector and BM25 search in parallel, limit reranking candidates, keep prompts short, and stream the answer so the first token arrives quickly. Caches for embeddings, retrieval, answers and prompt prefixes remove repeated work, with the user's access scope in any answer-cache key.

ReliabilityBackground work uses a transactional outbox, idempotent tasks, retries and reconciliation. Indexes are rebuilt as a new generation, validated and switched in one commit with rollback, and every call has a timeout with graceful fallbacks.

CostGPU time dominates, so I use right-sized or quantized models where evaluation allows, batching, caching and routing.

Don't say"We cache answers by question text."
Say instead"The key includes the user's access scope and the index generation, or the cache leaks or goes stale."
Don't say"We re-index the live collection when the model changes."
Say instead"We build a new generation alongside, validate it, switch in one step, and keep the old one for rollback."
