1What you will learn

  • How to build a golden evaluation dataset that reflects real use.
  • Retrieval metrics (hit rate, precision, recall, MRR, nDCG) and generation metrics (faithfulness, relevancy, correctness, citations).
  • How to use an LLM as a judge without fooling yourself.
  • The improvement loop: baseline → one change → compare → gate the release.

2Why it matters

RAG has many settings: parser, chunk size, embedder, k, fusion, reranker, prompt, model. Changing one often helps some questions and hurts others. Without measurement, every change is a guess and regressions reach users unnoticed. Evaluation turns "it feels better" into numbers you can compare.

3Core ideas

The golden dataset

  • Questions: real user questions where possible; synthetic questions generated from chunks to fill gaps.
  • Expected sources: document + page or section (these survive re-chunking better than chunk IDs). Optionally an expected answer.
  • Case types: factoid, multi-part, table lookup, ID or keyword lookup, multilingual, unanswerable (should abstain), adversarial (injection, off-topic).
  • Size: start with 50–200 reviewed cases; grow it from production feedback. Version and freeze each dataset.

4How it works

LLM-as-a-judge

  • An LLM scores answers against a rubric: "Is every claim supported by the context? Answer yes or no, with reasons."
  • Known biases: preferring the first option (position), longer answers (verbosity) and its own style (self-preference).
  • Calibrate: label 50–100 cases by hand and measure agreement with the judge before trusting it. Fix the judge model, version, prompt and temperature (0).
  • Prefer simple binary or 3-point judgments over 1–10 scales; they are more consistent.

The improvement loop

  1. Baseline: run the current published pipeline on the dataset and store the results.
  2. One change: a new chunk size, model or prompt — a new candidate pipeline version.
  3. Run and compare: per metric and per case. Look at regressions, not just averages.
  4. Gate: acceptance criteria (no critical metric below threshold, no regression beyond tolerance on any case type, latency budget met).
  5. Release after review; keep monitoring production with sampled checks and feedback.

5In the real world

  • Evaluate retrieval separately from generation. It tells you which half to fix (lesson 08).
  • Small datasets are noisy. A 2-point change on 60 questions may be chance — inspect the changed cases.
  • Keep unanswerable cases: they catch systems that always answer.
  • Tools: DeepEval (pytest-style metrics), RAGAS, TruLens. All can use a local judge model. Retrieval metrics are simple to compute yourself.
  • Add every production failure you fix as a new test case. The dataset becomes your regression suite.

6Common mistakes

  • Judging changes by trying a few questions by hand.
  • Only measuring the final answer, so you can't tell retrieval failures from generation failures.
  • Trusting an uncalibrated small judge model.
  • Changing three settings at once.
  • Evaluation cases leaking into fine-tuning data (lesson 26).

8Check yourself

Recall@10 is high but faithfulness is low. Where is the problem?
Generation: the evidence is retrieved, but the model doesn't stick to it — a prompt, context-assembly or model issue.
Why include unanswerable questions in the dataset?
To measure whether the system abstains correctly instead of inventing answers.
How do you know whether to trust an LLM judge?
Compare its judgments with human labels on a sample and measure agreement. Keep the judge version and prompt fixed across compared runs.
