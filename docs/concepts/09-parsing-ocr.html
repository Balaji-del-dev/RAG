1What you will learn

  • Why PDFs are hard: they store positioned glyphs, not paragraphs.
  • What parsers do: text, layout, reading order and tables. When to use PyMuPDF, Docling or a VLM.
  • When and how to run OCR (Tesseract, EasyOCR).
  • Quality checks and safety limits for parsing untrusted files.

2Why it matters

Garbage in, garbage out. If a table is flattened into a jumble of numbers, a two-column page is read across the columns, or a scanned page yields no text, no embedding model or LLM can recover. Parsing quality sets the ceiling for the whole system.

Why PDFs are hard

  • A PDF says "draw these glyphs at x, y". It has no notion of paragraphs, columns or tables.
  • Multi-column layouts, headers and footers, footnotes and side notes must be ordered correctly.
  • Tables are just text plus lines. The row and column structure has to be inferred.
  • Some fonts have no proper Unicode mapping, so "copyable" text comes out as garbage.

4How it works: tools and pipeline

PyMuPDF

Very fast text, block and word extraction with coordinates, plus images and page rendering. Good first pass and fallback.

Docling

Layout-analysis models find headings, paragraphs, lists, figures and tables. TableFormer reconstructs tables. Exports structured JSON or Markdown. Slower, but much better structure.

OCR: Tesseract / EasyOCR

Tesseract is classic, CPU-friendly and covers many languages (including Tamil and Hindi). EasyOCR is deep-learning based and uses a GPU if available. PaddleOCR is another strong option.

VLM document parsers

Vision-language models read page images directly, which helps with complex layouts. They are much slower and can hallucinate, so reserve them for hard pages.

  1. Detect type from the content (magic bytes), not just the file extension.
  2. Fast extract (PyMuPDF): measure text quality per page.
  3. Decide OCR per page: no text layer, or text that is mostly invalid characters → render at about 300 DPI and OCR.
  4. Layout and structure (Docling): reading order, headings, section path, tables kept as tables.
  5. Store artifacts (parser JSON, OCR output, page images) and record parser name and version.
  6. Quality checks before chunking (see below).

Tables deserve special care

  • Keep tables as Markdown or HTML tables, with the header row attached.
  • For large tables, chunk by groups of rows and repeat the header in each chunk.
  • Optionally store a one-line description ("Table 3: monthly fees by plan").

Security: parsers handle untrusted inputRun parsing with limits: timeout, memory, page count, file size. Reject encrypted or oversized files, guard against zip bombs, never execute macros, and isolate workers. Malformed PDFs have exploited parser bugs before (lesson 23).

6Common mistakes

  • OCR on everything: slow, and worse than the real text layer on born-digital pages.
  • OCR on nothing: scanned pages silently become empty documents.
  • Flattening tables into running text.
  • Dropping page numbers and section paths, so citations become impossible.
  • Not versioning parser output, so a parser upgrade can't be compared or rolled back.

8Check yourself

How can you tell, per page, that OCR is needed?
The page has no text layer, very few characters, or text that is mostly invalid or garbage characters. Render that page as an image and OCR it.
Why repeat the header row when splitting a large table into chunks?
Without headers, a chunk of rows has no column meaning. Embeddings and the LLM can't tell what each number refers to.
Why record the parser name and version with each artifact?
To reproduce results, compare parser upgrades on the evaluation set, and re-process only what changed.
