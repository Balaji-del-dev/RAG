2Why it matters

Users search for exact things: invoice numbers, error codes, product names, people, clause numbers, acronyms. Embeddings blur these (lesson 03). BM25 matches them exactly, is explainable, needs no model, and in many benchmarks remains a strong baseline. Combining both (lesson 16) is the standard for good reason.

3Core ideas

Inverted index

TermPosting list (document · positions)

carryc12 · [5] · c77 · [11]
e-4012c305 · [1]

For a query, the engine looks up each term's postings and scores only the matching documents. That is why lexical search is fast on huge collections.

Text analysis

"Carried-over Days"→ tokenizercarried · over · days→ lowercasecarried · over · days→ stemmercarri · over · dai

The same analyzer runs on documents and queries, so "carry over" can match "carried over". Language-specific analyzers handle stemming and stop words. Codes and IDs belong in keyword fields, which are not analyzed, for exact matches.

BM25

score(q, d) = Σ over query terms t:
    IDF(t) · tf(t,d) · (k1 + 1) / ( tf(t,d) + k1 · (1 − b + b · |d| / avgdl) )
  • IDF: rare terms count more ("E-4012" outweighs "the").
  • tf saturation (k1 ≈ 1.2): the 10th repetition of a word adds little.
  • Length normalization (b ≈ 0.75): long chunks don't win just by containing more words.

}
  • match: analyzed full-text search, scored by BM25. match_phrase: words in order. term: exact match on keyword fields.
  • bool query: must or should for scoring, filter for non-scoring constraints (access groups, document IDs, dates).
  • Field boosts: e.g. title^2. Highlighting returns the matching fragment, which is useful for citation snippets.

Learned sparse retrieval

Models such as SPLADE and BGE-M3's sparse output produce term weights, including related terms that are absent from the text. They keep the inverted-index speed and add some semantic matching. They are a middle ground between BM25 and dense vectors.

5In the real world

BM25 wins

  • IDs, codes, numbers, names
  • rare technical terms
  • quoted phrases
  • brand-new jargon

Dense wins

  • paraphrases, synonyms
  • natural-language questions
  • cross-lingual queries
  • vague descriptions
  • Choose analyzers per language. Test them with the _analyze API on real text, including Indic scripts.
  • Use dynamic: strict mappings so stray fields don't silently create bad mappings.
  • Disable refresh during bulk indexing (refresh_interval: -1) and re-enable it before validation.

6Common mistakes

  • Putting IDs and codes only in analyzed text fields, where they get split and mangled.
  • Using a should clause where a filter is needed, so access rules become "suggestions".
  • Default English analyzers on non-English text.
  • Dropping BM25 because "we have vectors now".

8Check yourself

Which query suits BM25 better: "error E-4012" or "why does my app crash at startup"?
"error E-4012": an exact rare code that BM25 matches directly. The second is a natural-language question better served by dense search (ideally both, fused).
What does the b parameter do?
It controls length normalization: with b = 1 long documents are fully penalized for their length; with b = 0 length is ignored.
Why put access groups in a bool filter, not should?
A filter is a hard constraint that excludes non-matching documents. should only changes the score, so forbidden documents could still appear.
