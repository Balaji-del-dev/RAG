2Why it matters

Dense search finds meaning; BM25 finds exact terms (lessons 13–14). Questions mix both: "What is the penalty in clause 7.3 for late delivery?" Hybrid search raises recall — the chance that the right chunk is among the candidates — and recall is the foundation everything later depends on.

3Core ideas

The score-scale problem

Cosine similarity lives roughly between 0 and 1, while BM25 scores are unbounded (3.2, 17.8, 41.0…) and depend on the query. Adding them directly lets BM25 dominate on some queries and vanish on others. You need either ranks (RRF) or normalized scores.

Reciprocal Rank Fusion

RRF(d) = Σ over result lists i:   wᵢ / (k + rankᵢ(d))        k ≈ 60, wᵢ = 1 by default
  • Only positions matter, so no calibration is needed between engines.
  • Documents found by both retrievers get two contributions and rise to the top.
  • k controls how fast credit falls with rank. Larger k flattens the differences between top ranks.

Weighted score fusion

score(d) = α · norm(dense(d)) + (1 − α) · norm(bm25(d))      norm = min-max or z-score per query

This can beat RRF when tuned well, but it is sensitive to outliers and needs tuning of α on an evaluation set. RRF is the robust default.

4How it works in a pipeline

  1. Run dense and BM25 searches in parallel, with the same filters, on the same index generation.
  2. Take enough candidates: typically top 20–100 from each.
  3. Normalize the candidates to one shape keyed by chunk ID, and dedupe.
  4. Fuse (RRF), keep the top 30–50, and pass them to the reranker (lesson 17).
Native vs application-level fusionQdrant can fuse dense and sparse vectors inside one query (prefetch + RRF), and OpenSearch has hybrid queries with normalization or RRF. When dense lives in Qdrant and BM25 in OpenSearch, fusion must happen in your application, as in this platform.

5In the real world

  • Hybrid + reranker is the most common production retrieval setup today.
  • Give a retriever more weight only when evaluation proves it — for example more BM25 weight for ID-heavy corpora.
  • Keep each retriever's original ranks and scores. They are essential for debugging ("found by BM25 only").
  • Dedupe at the parent or section level too, so five chunks of the same section don't fill the context.

6Common mistakes

  • Adding raw cosine and BM25 scores together.
  • Taking only the top 5 from each retriever, so fusion has nothing to work with.
  • Different filters on the two engines, so forbidden documents leak in through one side.
  • Searching two different index generations.

8Check yourself

Why does RRF not need score normalization?
It uses only rank positions, which are comparable across engines, never the raw scores.
A chunk is rank 1 in BM25 but absent from dense results. Can it still win?
Yes, if no chunk appears high in both lists. Chunks found by both usually win because they get two contributions.
Why must both engines use the same filters?
Otherwise one side can return documents the user must not see, or that are outside the requested scope, and fusion lets them through.
