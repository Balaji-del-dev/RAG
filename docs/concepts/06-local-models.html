1What does "running a model locally" mean?

Interview answer — say this first
In simple words

Instead of sending your data to an online AI service, you run the model on your own server with your own GPU. The model must fit into the GPU's memory. Quantization makes the model smaller so it fits, and a serving engine like Ollama or vLLM runs it and gives your app an API.

2Why do we need it?

Cloud API (e.g. a hosted model)

  • Your documents leave the company
  • Needs internet; not allowed in some offices
  • Cost grows with every token
  • The provider can change or remove the model

Local model

  • Data never leaves your servers (privacy, compliance)
  • Works fully offline
  • Fixed hardware cost, no per-token bill
  • You control the exact model version
Analogy: a desk, a book and notes

The GPU memory (VRAM) is your desk. The model weights are a huge book that must lie open on the desk. Each conversation needs its own notes (the KV cache), which grow as the conversation gets longer. Quantization is printing the book in a smaller font: it takes less space, with a small loss in quality. If it doesn't fit on the desk, part moves to normal RAM and everything becomes 10–50× slower.

3How does it work?

1

Choose a model and a size

Pick an open-weight model (Llama, Qwen, Mistral, Gemma) with a size your GPU can hold, such as 7–8B or 70B parameters.

2

Quantize it so it fits

Normally each parameter takes 2 bytes (16-bit). Quantization stores it with fewer bits, for example 4-bit (about 0.55 bytes). The model becomes about 4× smaller.

Example: 8B model: 16 GB at 16-bit → about 5 GB at 4-bit
3

Check that weights + KV cache fit in GPU memory

GPU memory needed ≈ weights + KV cache (grows with tokens and users) + 10–20% overhead.

4

Serve it with an engine

Ollama is the easy choice for a laptop or a small team. vLLM is built for many users at once on GPU servers. Both give an OpenAI-compatible API.

5

Put a gateway in front

A gateway such as LiteLLM gives the app one API for all models and adds routing, retries, timeouts and logging.

4Example: step by step

Will an 8B model for 4 users fit on a 16 GB GPU?
  1. Weights: 8 billion parameters. At 16-bit (2 bytes) = 16 GB — too big. At 4-bit (≈0.55 bytes) ≈ 4.5–5 GB.
  2. KV cache: ≈ 128 KB per token (lesson 04) × 8,000 tokens × 4 users ≈ 4 GB.
  3. Overhead: working memory and buffers ≈ 1–2 GB.
  4. Total ≈ 10–11 GB → it fits a 16 GB GPU, with room to spare.

Remember — the quick formula

Weights in GB ≈ billions of parameters × bytes per parameter. 7B at 16-bit ≈ 14 GB; at 4-bit ≈ 4 GB. Then add the KV cache.

5Important terms

VRAM

The GPU's own memory. The model and KV cache must fit here to run fast.

Quantization

Storing weights with fewer bits to save memory and gain speed, with a small quality loss.

GGUF

The single-file model format used by llama.cpp and Ollama (e.g. Q4_K_M, Q8_0).

AWQ / GPTQ / FP8

Quantized formats used on GPU servers such as vLLM.

Continuous batching

New requests join the running batch between steps, so the GPU is always busy.

PagedAttention

vLLM's way of storing the KV cache in small pages, so no memory is wasted.

TTFT, tokens/s, throughput

Time to first token · speed for one user · total tokens per second for all users.

Gateway

One API in front of many model servers: routing, retries, budgets and logs.

safetensors

A safe weight-file format that cannot run hidden code (unlike pickle files).

Open-weight model

A model whose weights you can download and run yourself.

7Advantages and limitations

Advantages

  • Full data privacy; works offline
  • No per-token cost
  • Exact, fixed model version
  • Can be tuned and quantized for your needs

Limitations

  • Needs GPUs: big upfront cost
  • Open models may be weaker than the best cloud models
  • You must handle updates, scaling and security
  • 4-bit quantization can reduce quality a little

Real example: running fully offline and safely
  1. Download every model file during setup and store it locally.
  2. Record each file's exact version and SHA-256 checksum, and check them at startup.
  3. Block downloads at runtime (for example HF_HUB_OFFLINE=1).
  4. Use safe formats (safetensors, GGUF) and never enable trust_remote_code for unreviewed code.
  5. Ollama and vLLM have no login by default: keep them on a private network and expose only the gateway.

In our platform

  • LiteLLM → Ollama or vLLM for answer generation. The gateway adds routing, retries and timeouts.
  • model_definitions records the provider, model name, revision and settings, so every answer can be traced to an exact model.
  • Architecture rule: all model files and dependencies are available locally.

9How to explain it in an interview

Your 1-minute answer

DefinitionRunning a model locally means serving an LLM on our own hardware instead of calling an external API, so the data never leaves the organization.

How it worksThe GPU must hold the model weights and the KV cache of active requests. Weights take about parameters times bytes per parameter, so a 7B model needs about 14 GB in 16-bit and about 4 GB in 4-bit. Quantization reduces this memory with a small quality loss.

ToolsI use Ollama for simple setups and development, and vLLM for production with many concurrent users, because continuous batching and PagedAttention give much higher throughput. A gateway like LiteLLM sits in front.

Trade-offWe gain privacy, offline operation and predictable cost, but we must manage GPUs, scaling and security ourselves, and evaluate the exact quantized model we deploy.

Don't say"A 7B model needs 7 GB."
Say instead"It depends on precision: about 14 GB in 16-bit, about 4 GB in 4-bit, plus the KV cache."
Don't say"Quantization has no quality cost."
Say instead"8-bit is almost lossless; 4-bit has a small loss. We evaluate the exact model we deploy."
Don't say"Ollama is the best choice for 200 concurrent users."
Say instead"For many users on GPUs, vLLM's continuous batching gives much higher throughput."
