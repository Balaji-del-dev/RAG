1What you will learn

  • How to estimate GPU or RAM needs for a model: weights + KV cache + overhead.
  • What quantization is (GGUF, AWQ, GPTQ, FP8) and what it costs in quality.
  • When to use llama.cpp, Ollama or vLLM, and what a gateway like LiteLLM adds.
  • How to serve embedding and reranker models, and how to run fully offline.

2Why it matters

An offline platform lives or dies by hardware fit. A model that does not fit spills to CPU and becomes 10–50× slower. A context window set too large leaves room for only one user. Knowing the memory math up front avoids buying the wrong GPU, or picking a model you can't run.

3Core ideas

Memory math

weights  ≈ parameters × bytes per parameter
           8B × 2 bytes (FP16)   ≈ 16 GB
           8B × 1 byte  (INT8)   ≈  8 GB
           8B × ~0.55 byte (4-bit) ≈ 4.5–5 GB
total    ≈ weights + KV cache (per token × tokens × concurrent requests) + 10–20% overhead

From lesson 04, Llama-3-8B needs about 128 KB of KV cache per token in FP16. So 4 users × 8K tokens ≈ 4 GB of cache on top of the weights.

Quantization

Quantization stores weights with fewer bits. Quality drops a little, while memory and speed improve a lot.

4Serving engines

llama.cpp

C/C++ engine for GGUF models. Runs anywhere (CPU, Apple, NVIDIA, AMD) and includes an OpenAI-compatible server. Great for small machines.

Ollama

A friendly wrapper around llama.cpp: model library, ollama pull, REST and OpenAI-compatible API, automatic chat templates. Easiest start; good for low to moderate concurrency.

vLLM

High-throughput GPU server: PagedAttention, continuous batching, prefix caching and an OpenAI-compatible API. The choice when many users share GPUs.

Others

SGLang, Hugging Face TGI, TensorRT-LLM, LM Studio. The same OpenAI-style API is common to all of them.

Latency vs throughput

  • TTFT (time to first token): dominated by prefill, so long prompts raise it.
  • ITL / TPOT (time per output token): sets how fast the text streams.
  • Throughput (tokens/second across all users): improved by batching. vLLM's continuous batching adds new requests between steps, so GPUs stay busy.

Gateways: LiteLLM

A gateway gives the application one OpenAI-style API to every backend. On top it adds routing, retries, fallbacks, timeouts, per-key budgets and logging. Swapping Ollama for vLLM, or one model for another, then becomes a configuration change instead of a code change.

Embedding and reranker models

  • Small encoders can run inside the worker process (sentence-transformers, ONNX Runtime), or as a service (Hugging Face Text Embeddings Inference, Infinity). Ollama and vLLM also serve some embedding models.
  • Batch embeddings (32–256 texts per call) for 10× better throughput during ingestion.

5In the real world: running fully offline

  1. Pre-download every model file during provisioning and store it locally (or in MinIO).
  2. Pin and verify: record the exact revision and SHA-256 of every file, and check them at startup.
  3. Block runtime downloads: for example HF_HUB_OFFLINE=1, and no "auto-pull" in production.
  4. Prefer safe formats: safetensors and GGUF. Avoid loading pickled .bin files from unknown sources, and never enable trust_remote_code for unreviewed code (lesson 23).
  5. Lock down the network: Ollama and vLLM have no authentication by default. Bind them to localhost or a private network, and expose only the gateway.

6Common mistakes

  • Sizing for weights only and forgetting the KV cache for context length × concurrency.
  • Evaluating on FP16 but deploying Q4 (or the reverse).
  • Letting a server download models at runtime in an "offline" system.
  • Exposing Ollama's port to the whole network.
  • Hard-coding one backend's API in application code instead of using the gateway.

8Check yourself

Roughly how much memory do the weights of a 14B model need at FP16, INT8 and 4-bit?
About 28 GB, 14 GB and 8 GB respectively, plus KV cache and overhead.
Why can vLLM serve more users per GPU than a simple server?
Continuous batching keeps the GPU busy with many requests at once, and PagedAttention packs KV caches efficiently, avoiding wasted memory.
What does a gateway such as LiteLLM give you?
One stable API for all model backends, plus routing, retries, fallbacks, timeouts, budgets and logging — so backends can change without code changes.
