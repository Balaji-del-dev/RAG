1What is a vector database?

Interview answer — say this first
In simple words

A vector database stores millions of embeddings and answers one question very fast: "which stored vectors are closest to this question vector?" It uses a smart index (usually HNSW) so it doesn't have to compare the question with every vector one by one.

2Why do we need it?

Comparing the question with every stored vector is called exact search. With 10,000 chunks that is fine. With 10 million chunks it is far too slow for a chat app. A vector database uses approximate nearest neighbour (ANN) search: it may very rarely miss one true neighbour, but it is thousands of times faster.

Exact search (compare with all)

  • Always 100% correct
  • Time grows with every vector added
  • Too slow for millions of chunks

ANN index (HNSW)

  • Finds results in milliseconds
  • Recall usually 95–99%+
  • Also filters by metadata and compresses vectors
Analogy: finding a house in a new city

Exact search is knocking on every door in the city. HNSW works like a road network: first take the highway (a top layer with few, far-apart points) to get near the right area, then main roads, then small streets (the bottom layer, which has every point). You reach the right house in a few dozen steps instead of millions.

3How does it work?

How an HNSW search works

1

Build a layered graph (at indexing time)

Each vector is a point, linked to its closest neighbours. The bottom layer has all points; each higher layer has fewer points with longer links, like highways.

2

Start at the top layer

The search starts at a fixed entry point on the sparse top layer.

3

Always move closer

Move to whichever neighbour is closer to the question vector. Repeat until no neighbour is closer.

4

Go down a layer and repeat

Drop to the next, denser layer and continue from the same point.

5

Return the top k from the bottom layer

On the bottom layer, keep a list of the best candidates (size ef) while exploring, then return the top k.

The three HNSW settings to know

SettingMeaningEffect
Mnumber of links per pointhigher → better recall, more memory (typical 16–32)
ef_constructsearch width while building the graphhigher → better graph, slower indexing (typical 100–400)
ef (at search time)search width for each questionhigher → better recall, slower queries

4Example: step by step

How much memory do 1 million chunks need?
  1. Vectors: 1,000,000 chunks × 1,024 numbers × 4 bytes (float32) ≈ 4.1 GB.
  2. HNSW links (M = 32): about 0.25 GB.
  3. Plus the payload (metadata) for each point.
  4. With int8 quantization, the vectors in RAM shrink to about 1 GB (4× smaller).
"Show me only my department's documents"

Each point in Qdrant has a payload like {"document_id": "...", "department": "HR", "access_groups": ["hr-team"]}, with a payload index on access_groups. Every search includes the filter "access_groups contains the user's groups", applied during the HNSW search, so the results are both fast and permitted.

Remember — filter during the search, not after

If you search first and filter afterwards, a strict filter (e.g. only 1% of documents allowed) can leave you with zero results. Filtering during the search with payload indexes always returns enough permitted results.

5Important terms

kNN (k-nearest neighbours)

The k stored vectors closest to the question vector.

ANN (approximate nearest neighbour)

Finds almost exactly the nearest neighbours, but much faster.

HNSW

Hierarchical Navigable Small World: a layered graph index, the most common ANN method.

IVF

Inverted File index: groups vectors into clusters and searches only the nearest clusters.

PQ (product quantization)

Compresses vectors into short codes to save a lot of memory.

ANN recall

The share of the true nearest neighbours that the index actually returns.

Payload

Metadata stored with each vector: document ID, page, access groups.

Quantization + rescoring

Keep compressed vectors in RAM for speed, then re-score the top results with the full vectors.

7Advantages and limitations

Advantages

  • Millisecond search over millions of vectors
  • Metadata filtering for access control
  • Quantization saves memory
  • Scales across machines

Limitations

  • Approximate: can miss a true neighbour
  • HNSW uses a lot of RAM
  • Settings (M, ef) need tuning
  • Another system to run, back up and keep in sync

9How to explain it in an interview

Your 1-minute answer

DefinitionA vector database stores embedding vectors with their metadata and finds the vectors most similar to a query vector.

How it worksComparing with every vector is too slow at scale, so it uses approximate nearest neighbour indexes such as HNSW. HNSW builds a layered graph: the search starts on a sparse top layer, moves greedily toward the query and refines on denser layers, reaching the nearest vectors in milliseconds.

TuningM and ef_construct control graph quality and memory; ef controls the recall–speed trade-off at query time. Quantization reduces memory, with rescoring to recover accuracy.

In practiceMetadata filters such as access groups are applied during the search, using payload indexes, so results are both fast and permitted.

Don't say"Vector search always returns the exact nearest neighbours."
Say instead"ANN trades a small loss of recall for speed. We measure ANN recall against exact search."
Don't say"We filter the results after the search."
Say instead"We filter during the search with payload indexes; otherwise strict filters can return too few results."
