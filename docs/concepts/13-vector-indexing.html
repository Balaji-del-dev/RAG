2Why it matters

With a million chunks, comparing the query vector to every stored vector takes too long per question, and it gets worse with every upload. ANN indexes find "almost exactly" the nearest neighbours in milliseconds. Their settings decide your recall, latency and memory bill.

3Core ideas

Exact vs approximate

  • Exact (flat) search: compare with all N vectors, about N × d multiplications. Fine up to around 100,000 vectors.
  • ANN: an index structure visits only a small part of the data. It may miss a few true neighbours. That loss is ANN recall, often 95–99% at the right settings.

HNSW — Hierarchical Navigable Small World graphs

ParameterMeaningEffect
M (or m)links per nodehigher → better recall, more memory; typical 16–32
ef_constructsearch width while buildinghigher → better graph, slower indexing; typical 100–400
ef (hnsw_ef, at search time)search width per queryhigher → better recall, slower queries; tune per latency budget

Other index types: IVF (cluster vectors, search only nearby clusters), PQ (compress vectors into short codes) and DiskANN (graph on SSD for billions of vectors). HNSW is the default in Qdrant, OpenSearch k-NN and pgvector.

4How it works in practice

Filtering

Real queries come with filters: this document, this department, the user's access groups, dates. Options:

  • Post-filter: search, then drop non-matching results. You may end up with too few results.
  • Pre-filter / filtered search: apply the filter during graph traversal. Qdrant builds payload indexes and adapts its search plan to how selective the filter is.
Index the payload fields you filter onIn Qdrant, create payload indexes (keyword, integer, datetime) for every filtered field, such as document_id, access groups and dates. Without them, filtered search slows down sharply.

Quantization inside the vector database

MethodMemoryNotes
float32 (none)1×baseline
Scalar (int8)¼small recall loss; a safe default at scale
Binary1/32very fast; needs rescoring with original vectors; works best with high-dimensional models
Product quantization1/8–1/64more recall loss; for very large collections

A common pattern: quantized vectors in RAM for search, originals on disk, then rescore the top candidates with full precision.

Memory estimate

1,000,000 chunks × 1,024 dims × 4 bytes ≈ 4.1 GB  (float32 vectors)
+ HNSW links ≈ N × M × 2 × 4 bytes ≈ 0.25 GB (M = 32)
+ payload and payload indexes
int8 quantization → vectors ≈ 1 GB in RAM (originals can stay on disk)

5In the real world

  • Vector database features that matter: upsert and delete by ID, payload filters, collection aliases, snapshots, replication and sharding, quantization, on-disk storage.
  • pgvector (a PostgreSQL extension) is great for small and medium corpora and keeps one database. Dedicated engines such as Qdrant scale and filter better.
  • Measure ANN recall: compare HNSW results to exact search on a sample of queries after every index change.
  • Deletes leave work for the index to clean up later. Build a fresh collection when re-indexing everything (blue-green, lesson 25).

6Common mistakes

  • A distance metric that doesn't match the embedding model.
  • Filtering on fields without payload indexes.
  • Default ef at very high filter selectivity, so few or no results come back.
  • Mixing vectors of different models or dimensions in one collection.

8Check yourself

What does raising ef at search time do?
The search explores more candidates: higher recall, higher latency. It doesn't change the stored index.
Why can post-filtering return too few results?
The ANN search returns top-k first; if most of them fail the filter, little or nothing is left. Filtering during search avoids this.
What is rescoring, and why is it used with binary quantization?
After a fast search on compressed vectors, the top candidates are re-scored with full-precision vectors. This recovers the accuracy lost by heavy compression.
