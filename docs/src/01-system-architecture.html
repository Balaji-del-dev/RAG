Qdrant

  • dense vectors · HNSW
  • collection per generation
  • point ID = chunk ID
  • payload filters: document, version, generation, page
Published only after both indexes pass validation — never one ahead of the other.

OpenSearch

  • BM25 full-text + exact keywords
  • versioned index per generation
  • explicit mappings & analyzers
  • _id = chunk ID
Rollback & rebuild
the previous generation stays until nothing references it · both indexes can be rebuilt from canonical chunks in PostgreSQL (vectors are re-embedded)

7 · Quality & operations

Observe, evaluate, improve

Flower

Celery worker and task visibility: queues, retries, failures, runtimes. Reads task events through the Redis broker.

DeepEval

Retrieval and answer quality tests (faithfulness, answer relevancy, contextual precision and recall) run as Celery evaluation tasks; results land in evaluation_results. The LLM judge runs locally through Ollama — calibrate it against human-labelled cases.

User feedback & failure analysis

Ratings in user_feedback; reviewed problems in failure_cases with root cause and resolution. Reviewed cases are added to the golden dataset.

Langfuse

Request traces, prompts, model calls and timings, joined to retrieval_runs.trace_id. Send IDs and metrics by default; prompts and document text only where policy allows.
Scope conflict: Langfuse v3 self-hosting needs PostgreSQL, ClickHouse, Redis and S3 storage and ships as Docker Compose or Kubernetes — decide on that exception before building.

Architecture rules

  1. PostgreSQL is the source of truth for metadata and lifecycle state.
  2. MinIO is the source of truth for stored file contents.
  3. Qdrant and OpenSearch are derived indexes, not the document store.
  4. Django coordinates work; Celery handles long-running operations.
  5. Index publication waits for validation across both search systems.
  6. An answer is not grounded just because the LLM returned text.
  7. All model files and runtime dependencies are available locally.
