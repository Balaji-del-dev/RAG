Source of truth · file contents

MinIO S3 API

Owns bytes: uploaded originals, parser and OCR output, generated files. PostgreSQL stores bucket + object key + object version + SHA-256. Django and Celery reach it only through the S3 API (boto3 / django-storages).
rag-originals/ # versioning on └── documents/<document_id>/ └── v<version_number>/<sha256>.<ext> rag-artifacts/ └── <document_version_id>/<job_id>/ ├── docling.json · pymupdf.json ├── ocr/page-0001.json ├── normalized.md · structure.json └── tables/table-001.csv rag-exports/ # generated files └── evaluations/<evaluation_run_id>/

Rules

  • object keys are generated by Django — never the client's filename
  • bucket versioning on originals; storage_version_id pins the exact object
  • SHA-256 computed on upload and re-checked when a worker reads the object
  • objects are deleted only after lifecycle checks: no published generation or retained version still references them
Supply risk: MinIO's community edition has been source-only since October 2025 and its repository was later archived. Pin a release you build and verify yourself, or swap in another S3-compatible store (SeaweedFS, Garage, Ceph RGW) — behind the S3 API boundary that is a configuration change.

Database conventions

  • UUID primary keys; FKs and check constraints everywhere
  • status columns are enums (Django TextChoices)
  • schema changes only through Django migrations
  • JSONB for flexible detail; never for IDs, scores or statuses
  • partition retrieval_results / audit_events only when volume demands it
  • backups: PostgreSQL PITR + MinIO versioned buckets; indexes are rebuildable
Dispatch & sync

Outbox dispatcher

  1. Claim pending rows 
    SELECT … FROM outbox_events
WHERE status='PENDING'
  AND available_at <= now()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 200;
  2. Publish the Celery task, then mark the row DISPATCHED
Redis — Celery broker only. Losing it loses queued messages, never state: undelivered rows are re-dispatched from the outbox.
Celery index builder
  1. Upsert / delete in Qdrant and OpenSearch keyed by chunks.id — safe to repeat
  2. Update index_memberships; retry with backoff; failures stay visible for reconciliation

Write path

Upload & ingest a document

  1. Django checks the user's upload permission and the access groups they assign, then extension, sniffed MIME type, size and content, then SHA-256; an exact duplicate returns the existing status.
  2. Original → MinIO under a generated key; one transaction writes document_versions, document_access_grants, processing_jobs and an outbox_events row.
  3. The dispatcher publishes the Celery task via Redis; workers read MinIO and write artifacts back as extracted_artifacts.
  4. Canonical chunks and embedding_records go to PostgreSQL; the index builder fills Qdrant and OpenSearch and marks memberships.
  5. Failed steps keep their error; retries reuse the same chunk IDs, so nothing is duplicated.
Coordinated publication

Publish an index generation

  1. Build the new Qdrant collection and OpenSearch index for generation N+1.
  2. Compare expected and actual counts; check for missing, duplicate and orphaned records.
  3. Run dense, lexical and hybrid smoke searches; store each result in index_validations.
  4. One PostgreSQL transaction marks N+1 PUBLISHED and N RETIRED — only after both indexes pass.
  5. Keep N for rollback; drop it once no run, evaluation or retention rule references it.
Read path

Answer a question

  1. Authenticate the session; load the user's roles and access groups from PostgreSQL. Read the published index_generation → both physical names; create retrieval_runs with request ID, trace ID and user_id.
  2. Dense (Qdrant) and BM25 (OpenSearch) with the same filters — published generation and the user's access groups → retrieval_results with original ranks and scores.
  3. RRF + dedupe by chunk ID → fusion_rank; cross-encoder → reranker_score.
  4. Context comes from canonical chunk text in PostgreSQL; the answer and citation_data → answer_records.
  5. Langfuse spans carry IDs, timings and token counts; prompts and document text only where policy allows.
Change & delete

New versions and deletions

  1. A changed file → new document_versions row (parent_version_id = previous); the old one becomes SUPERSEDED once the new one is PUBLISHED.
  2. Superseded or deleted chunks leave both indexes through index.delete outbox events.
  3. Delete → deleted_at + DELETED; invalidated in both indexes before any MinIO cleanup.
  4. MinIO objects are removed only after lifecycle checks; storage_objects prevents deleting shared bytes.
  5. Access change → document_access_grants updated and an index.acl outbox event rewrites access_groups in both indexes.
  6. audit_events records sign-ins, uploads, publications, deletions, role and access changes, and configuration changes.
PostgreSQL decides which generation is liveQdrant and OpenSearch cannot switch together, so a generation becomes live by one PostgreSQL commit. The query orchestrator then addresses both physical names from that row; aliases are only for operators and tools.
Why an outbox in front of CeleryPublishing from transaction.on_commit still loses the task if the process dies after COMMIT but before Redis receives it. The outbox row survives that crash and is re-dispatched; idempotent tasks make a double dispatch harmless.
Permissions live in the query, not the promptThe user's access groups come from the server-side session and are added as a mandatory filter to both searches, so text a user may not read never reaches the LLM. Answer caches include the user's access scope in their key.
Indexes are rebuildableVectors live only in Qdrant, so a rebuild re-embeds from canonical chunk text in PostgreSQL. To skip re-embedding, export each generation's vectors to rag-artifacts/ in MinIO.
